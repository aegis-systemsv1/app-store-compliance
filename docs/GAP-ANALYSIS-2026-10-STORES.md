## Apple App Store submission-readiness gap analysis (AEGIS vs Apple first-party sources)

- AEGIS repo: `aegis-systemsv1/app-store-compliance`, branch master, commit c89b823 (read-only; nothing modified)
- Verification date: 2026-10-04. Sources: developer.apple.com only (App Review Guidelines page shows **Last Updated: June 8, 2026**; Upcoming Requirements page; Apple Developer News RSS through 2026-10-02; App Store Connect Help; Apple documentation JSON).
- Scope: iOS/iPadOS App Store submission readiness. macOS-only items (notarization, Rosetta, Developer ID Sub-CA) noted but not scored.
- Compliance-pack status: **none** of the items below exist in compliance-pack format. `compliance-pack/exports/compliance-pack-v1.0.0.json` holds 12 AU privacy requirements only. Every Apple item lives in prose docs or `data/rejection-patterns.json` / `data/regulatory-deadlines.json`, which have no `evidence_method`, `applicability_conditions`, `last_verified_date`, `source_url` per item, or `release_blocking_policy`.

Bucket rule used: an item goes to NOT APPLICABLE TO SHIPSURE AUTOMATION only when no repository signal can help (pure App Store Connect / account / owner judgement). Items with any useful repo signal are bucketed by AEGIS coverage even if final proof needs owner evidence (evidence_method HYBRID).

## Fitting Apple requirements into the existing compliance-pack schema

These are observations about the schema, not changes. Nothing was edited.

- `status` enum is `CURRENT_LAW | ENACTED_FUTURE_COMMENCEMENT | PROPOSED_CONSULTATION | GUIDANCE_GOOD_PRACTICE`. Apple store requirements are contractual platform policy, not law. Labelling them `CURRENT_LAW` misstates them. Labelling them `GUIDANCE_GOOD_PRACTICE` would make every consumer treat them as never-blocking, which defeats "ready to submit". A schema decision is needed: add something like `PLATFORM_POLICY_CURRENT` / `PLATFORM_POLICY_FUTURE`, or a separate `instrument_type`, together with a validator rule.
- `legislation` (title, amending_act, source_url) is legally framed. For Apple items it would hold e.g. "App Review Guidelines 5.1.1(v)" with the guidelines URL. That works, but a `section`/`guideline_number` field would be cleaner.
- `jurisdiction` would be "GLOBAL", with storefront-specific items (EU, BR, KR, AU, VN, US-TX) set as regions. `regulator` would be "Apple Inc. (App Store)".
- Month-only effective dates ("September 2026", "April 2027", "early 2027") need a convention. AEGIS's deadlines file already uses first-of-month plus a note.

## Bucket rules used

Every requirement goes into exactly one bucket. Where more than one could apply, this order decides: (1) **NEEDS UPDATE** if AEGIS states something wrong or out of date; (2) **MISSING** if AEGIS has nothing on it; (3) **NOT APPLICABLE TO SHIPSURE AUTOMATION** ("NA-AUTO") if the requirement is met only by a Play Console declaration, an account action or human judgement, and nothing in a repo can show it; (4) **PARTIALLY COVERED**; (5) **EXISTING AND CURRENT**. NA-AUTO items still become `OWNER_EVIDENCE` requirements. Their notes column records how AEGIS covers them today.

## (c) Recent official changes AEGIS does not yet reflect (or reflects wrongly)

1. **READ_CALL_LOG call-verification removal takes effect 27 Jan 2027, not 26 Aug 2026.** Sources: Policy Deadlines PCH 12253906 and the PCH 10208820 banner. Wrong in `GOOGLE-PERM-SMS-CALLLOG`, GOOGLE-PLAY.md and GAP-ANALYSIS-2026-09.
2. **Play Billing Library ladder is off by one version.** New apps and updates need v9+ by 31 Aug 2027 (extension 1 Nov 2027) and v10+ by 31 Aug 2028. AEGIS says v8 in 2027 and v9 in 2028. Also, unmaintained existing apps don't need updates.
3. **16 KB memory page-size requirement.** Apps targeting API 35+ must support it, and updates without support are blocked from 1 Feb 2027. Not in AEGIS at all.
4. **Health apps declaration and Financial features declaration apply to all apps,** not only health or finance apps.
5. **AccessibilityService policy now forbids autonomous/agentic AI use** (only rule-based automation is allowed). Relevant to AI-assistant apps.
6. **Contacts policy:** Play Console declaration prompts started in September 2026. Picker intent is `Intent.ACTION_PICK_CONTACTS`. A 30-day self-extension is available after 27 Jan 2027.
7. **Data safety precise/approximate location guidance** (15 Jul 2026).
8. **Age-Restricted Content and Functionality** covers core dating/matchmaking and real-money gambling (Oct 2025), with the incidental-dating exception (Apr 2026). AEGIS only encodes the anon/random-chat leg.
9. **Prediction-market real-money apps must enroll in the global pilot** (by 1 Jun 2026).
10. **The consolidated Developer Program Policy page (PCH 18258653) is headed "effective September 30, 2026".** AEGIS says it was restructured "26 August 2026". Google also introduced a standardized policy numbering system (15 Jul 2026), so Compliance Pack citations should record those numbers.
11. **Personal loans country updates:** India approved-apps list (Oct 2025), Thailand listing disclosures by 4 Mar 2026, Pakistan short-term exception (Jul 2025), line-of-credit apps in scope (Apr 2025).
12. **Advertising ID:** the AD_ID manifest declaration threshold is targeting Android 13, not 12. Use App Set ID for non-ads uses.
13. **Store-readiness basics missing entirely:** AAB, Play App Signing, 64-bit native libraries, required listing graphics (feature graphic 1024×500, ≥2 screenshots, 512 icon), REQUEST_INSTALL_PACKAGES declaration, Google-specific sign-in-details rules.
14. **Stale target-API text** in PLATFORM-MECHANICS-2026 §2.5/§4 and the PRE-SUBMISSION-CHECKLIST mechanics gate ("35 today, plan for 36", flagged unverified). DAC confirms API 36 from 31 Aug 2026, extension to 1 Nov 2026 (page last updated 2026-10-01).
